# How this repo is tested

This project was written with an AI coding agent, which changes what a test suite
is for. The risk is not that a human forgot a case; it is that code and tests were
written together from the same assumption, so both are wrong in the same way and
the suite is green anyway. Every choice below is aimed at that failure mode:
measure what is covered rather than assume it, generate inputs instead of choosing
them, and check that the tests actually fail when the code is broken.

Run everything the way CI does:

```bash
./ci-local.sh                       # every gate, exactly as GitHub runs it
./ci-local.sh Coverage              # one gate by name fragment
```

The runtime is **stdlib only** and stays that way. Three measuring gates need pip
packages (`coverage`, `hypothesis`); they ask `tests/testpy.sh` for an
interpreter that has them, and a developer sets that up once:

```bash
python3 -m venv .venv-test && .venv-test/bin/pip install coverage hypothesis
```

## The layers

| layer | where | what it answers |
|---|---|---|
| Unit and contract | `tests/test_*.py`, `dashboard/tests/test_*.py` | does this function do what its docstring says, on the inputs this box really produces? |
| Fixtures from the real box | `dashboard/tests/fixtures/` | does the parser survive the output the actual commands print, French locale, `[N/A]` and all? |
| Hostile input sweeps | `test_cockpit_collectors.py`, `test_cockpit_http.py` | does anything raise, crash a thread, or return a plausible wrong number when the input is nothing like expected? |
| Property-based | `dashboard/tests/property_checks.py` | does the invariant hold for **every** input, not the ones we thought of? |
| Fuzzing | `tests/proxy_fuzz.py` | can generated bytes get the proxy to raise, rewrite a good body, or drop a pattern it should keep? |
| Simulation | `tests/proxy_fuzz.py` (`RelaySimulation`) | across generated sequences of client behaviour, is the engine ever left generating for a client that is gone? |
| Concurrency | `dashboard/tests/test_concurrency.py` | with 24 callers firing at one instant, does exactly one privileged action start, is the loser told, and is the lock always released? |
| Mutation | `tests/mutation.py` | if the code were wrong, would any of the above notice? |
| Browser | `dashboard/tests/*.mjs` | does the page work in a real headless Chromium, at four iPhone geometries? |
| Anti-drift | CI steps | do the four places that must agree still agree (targets, flags, sudoers allowlist, pins)? |

## Coverage is a floor, not a badge

`ci.yml` measures branch coverage per module and fails under a floor. The floors
are the numbers measured on 2026-09-10 minus a point of slack, and they are
**raised in a commit, never lowered quietly**:

| module | floor | why it is where it is |
|---|---|---|
| `lifecycle.py` | 95% | pure logic, no excuse |
| `recipes.py` | 95% | pure logic |
| `agent_relay.py` | 88% | the rest is socket error paths |
| `registry.py` | 88% | the rest is filesystem error paths |
| `cockpit.py` | 52% | 1,889 lines, most of it collectors that shell out; the auth, CSRF, static and action surfaces are covered, the sampler threads are not |

It was 14% on `cockpit.py` and 68% overall before 2026-09-10. Measuring is what
made that visible: nobody had ever run coverage on this repo.

## Property-based checks

`property_checks.py` states invariants over generated inputs. The ones worth
naming, because each is a class of bug rather than a case:

- every parser returns a value and never raises, for any text (they read
  journals, container logs and configs other tools wrote);
- `outcome_kind` is total: every string maps to one of five kinds, so the UI
  never has to guess;
- `_switches` matches whole arguments, so `--disable-radix-cache` can never
  answer for another flag;
- `drift(p, p) == []` for any profile, and drift is symmetric in the keys it
  finds;
- `oc-fit-limits.fit(pool, ceiling)` never grants more than the pool, never a
  negative budget, always whole thousands, and never less context for a bigger
  pool.

The relay boundary gets the same treatment, because it puts a browser interface
on a tailnet in front of an opencode that can run commands: only the relay's own
origin is ever allowed, `null` never is (a sandboxed iframe and a `file://` page
both send it), `host_name` never returns a port, no caller header survives under
a name the relay owns (Host, Authorization, Connection, Upgrade), and the
upstream can never set a cookie named like the cockpit session, which would be
session fixation on the cockpit.

Two of these tests were wrong before the code was: one asserted `fit` always
returns a positive budget, which is false and taught the real contract (it rounds
down to a thousand, so a pool too small for a thousand-token answer correctly
returns `(0, 0)`); another expected an `Upgrade` header on a non-websocket
forward. Both were rewritten to state what the code actually promises. That is
the method working: a property you cannot state correctly is a contract you did
not understand.

## Fuzzing and simulation

The keepalive proxy is the only component that reads bytes it does not control,
so it gets both. The fuzz properties are the interesting half: a body with
nothing wrong in it comes back **byte-identical**, a `pattern` Python can compile
is **never** dropped, a dropped one **genuinely does not compile**, the result is
valid JSON whenever it changed, and sanitizing twice changes nothing more. That
matters because the v6.13 fix exists to stop one tool schema from killing a
session; a sanitizer that quietly rewrote good bodies would be the worse bug.

`RelaySimulation` is a state machine, not a script. Hypothesis generates
sequences of client behaviour (read nothing and vanish, read a little and vanish,
stay to the end, on either dialect, with or without a slow prefill) against a
real proxy and a fake engine that reproduces SGLang's abort rule: an abort for a
rid whose state is gone is **recorded as ignored, not as an abort**. After every
step two invariants are checked: no abort was discarded by the engine, and no
request was aborted with an id the engine never had (in particular, never a
locally minted `msg_<uuid>`). That is the production bug of 2026-09-09 expressed
as a property instead of a story.

## Mutation score

`tests/mutation.py` edits one operator at a time in a module (comparison,
boundary, arithmetic, boolean, constant, `not`) and runs that module's suite after
each edit. A mutant the suite does not catch is a line the suite covers but does
not check.

```bash
python3 tests/mutation.py --all                                  # every module, against its floor
python3 tests/mutation.py dashboard/lifecycle.py "python3 dashboard/tests/test_lifecycle.py"
```

First run on `lifecycle.py`: **74.8%**, 53 survivors out of 210 mutants. The
survivors were read one by one and turned into the two `MutantsThatSurvived`
classes in `test_lifecycle.py`, each test naming the mutant it kills. Second run:
**90.8%**. What is left is mostly equivalent mutants, which no test can kill:
`weight_ends >= 2` sits next to an `or` clause that already covers the boundary,
and `pool <= 0` is unreachable past the `not pool` in front of it. One survivor
was removed by deleting code instead of adding a test: an `if` whose body was
`pass` decided nothing, so four mutants in it were undetectable by construction.

The tool had two bugs of its own, both worth recording because they are the
failure modes of every home-made mutation runner.

**Stale bytecode.** CPython validates a `.pyc` against its source mtime **and
size**, so two mutants written inside the same mtime granularity with the same
length are indistinguishable to that check and the interpreter silently re-runs
the previous mutant's bytecode. That reported a mutant as surviving which the
suite kills in one second by hand. It now sweeps `__pycache__` and runs with
`PYTHONDONTWRITEBYTECODE=1`. The first 94.2% it printed was not real; 90.8% is.

**Mutating the working tree.** The first version edited the real file and restored
it in a `finally`, which is wrong twice: anything else reading the repo at that
instant sees a mutant (a parallel test run reported 46 errors and one baffling
parse failure, which was this tool editing `recipes.py` underneath it), and a
`kill -9` between the write and the restore leaves a mutated source staged for
commit. It now copies the repo to a temp directory and mutates the copy, so a
killed run cannot touch the tree at all. Verified by killing one mid-walk and
checking `git diff`.

## Concurrency

Threads make failures probabilistic, so `test_concurrency.py` hammers rather than
samples: 24 callers released from one barrier, eight attempts per property. What
it pins is the cockpit's entire safety story, that only ONE privileged action
ever runs:

- exactly one caller gets 202 and the other 23 get `409 busy` with the running
  job named, whatever the interleaving;
- a refused parameter (400) and an unknown action (404) never take the lock, so
  they cannot cost the next caller its turn;
- the lock is released even when starting the job raises, which is why
  `start_action` catches around it (the test makes it raise on purpose);
- the audit log has one unbroken JSON line per started job, parsed back to prove
  no line was torn by two writers;
- the state snapshot the SSE stream serializes stays serializable while four
  samplers write into it, the event ring stays bounded under six writers, and
  `CpuTracker` never returns a percentage outside 0 to 100 while sampled from
  four threads.

Writing these found test pollution rather than a product bug, which is itself
worth recording: a `tearDown` that released the job lock while the job thread
still held it made `run_job`'s own release raise `release unlocked lock` in a
background thread, printing a traceback that reads exactly like a product defect.
The suite now waits for the lock instead of taking it.

## What the tests found

Not a hypothetical list. Every item below was found by writing the tests above,
on code that was already in production:

- **21 unauthenticated or authenticated crash paths in the cockpit.** Valid JSON
  of the wrong shape (`{"key": null}`, a non-object body, non-dict `params`)
  reached `.get()` and `hmac.compare_digest()` and raised, killing the handler
  thread and dropping the connection with no answer. Five are reachable before
  authentication. One assumption in three places; fixed at the boundary and
  pinned by a `MalformedJson` class that keeps every one of the 21.
- **A drift panel blind to a whole class of flag.** Recipes held flags as
  "flag -> value" pairs, so `--sleep-on-idle` had no representation and the panel
  whose job is to say where the box differs from the repo had nothing to report
  about a lane missing it.
- **A benchmark printing the wrong reference.** `bench.sh` announced the 27B lane
  and its baseline whatever lane was serving, so a normal 41.9 tok/s on the flash
  lane read as a regression against another model's number.
- **A feed painting a client that walked away in the same red as a dead engine**,
  because the browser was matching outcome strings with one rule: not `ok` means
  failure.
- **Test pollution that reads like a product bug**: a `tearDown` releasing the
  cockpit's single-job lock while the job thread still held it made `run_job`'s
  own release raise in a background thread.

## Conventions

- Every test file **runs its own tests when invoked directly** (`python3
  tests/test_x.py`), and CI counts what ran against what the file declares. A
  file with 58 tests and no `__main__` block once exited 0 having run nothing:
  silence is not a pass.
- Fixtures are **real output from the reference box**, trimmed, not invented.
  A French `free -g`, an `[N/A]` from `nvidia-smi` on unified memory and a
  `Received output for rid=...` flood line are all in `dashboard/tests/fixtures/`.
- A test names the bug it prevents, in the words of what went wrong. `git log`
  and `CHANGELOG.md` carry the story; the test carries the guard.
- Nothing in the offline suite touches the box: no network, no docker, no
  systemctl, no real API key. `test_cockpit_collectors.py` asserts that too, by
  recording every argv its stub was asked for.
